A reusable context file

## Analysis contract
- State phenotype, ancestry, build, and effect allele.
- Preserve source data. Write to explicit derived paths.
- Check IDs, duplicates, missingness, and join cardinality.

## Implementation
- R is primary. Prefer data.table for large tables.
- Use loops when they improve clarity or performance.
- Record package versions and random seeds.

## Validation
- Start with synthetic data and a small test region.
- Report what was run and what remains unverified.
Illustrative instructions, not a quotation from an active project. Add the actual project’s model, data conventions, and execution requirements before use.

A reviewable workflow

  1. InspectFind existing code, inputs, conventions, and prior results.
  2. PlanSpecify the model, change, outputs, and acceptance checks.
  3. ImplementKeep the change small enough to review.
  4. ValidateInspect failures, diagnostics, and scientific invariants.
  5. RecordSave the diff, command, environment, and limitations.
Suggested workflow. Scale the review to the consequence of the change. A formatting fix and a new association model require different validation depth.

Permissions and checkpoints

Bounded routine work

  • Read approved source files
  • Edit a dedicated working copy
  • Run tests on synthetic fixtures

Explicit project decisions

  • Protected-data access and external transfer
  • Large job arrays or paid services
  • Source overwrites, publication, or deployment

Use enforceable controls and a defined task scope.

This is a proposed checkpoint policy, not a claim about any vendor’s defaults or an institution’s approved tools. Existing project authorization should define what routine actions can proceed.

Code isolation with worktrees

# Development branch with its own checkout
git worktree add -b agent/variant-qc ../variant-qc

# Separate checkout of a committed analysis version
git worktree add --detach ../analysis-run HEAD

git -C ../analysis-run rev-parse HEAD

Use distinct output directories and keep the run checkout unchanged until jobs finish.

Git worktree manual

Git worktrees provide separate working directories but share repository objects and some repository state. A detached checkout is still writable. Do not treat a worktree as a security boundary or automatic data/output isolation.

An analysis specification

Illustrative request

Adapt the existing gene-based rare-variant workflow for a specified phenotype and chr22 pilot. First confirm the genome build, genotype and annotation format, sample matching, null model, relatedness handling, and variant masks. Propose MAF/MAC and missingness checks. Stop before a full-cohort submission.

A method name and a list of covariates are only part of the specification.

STAARpipeline documentation

STAARpipeline supports single-variant and variant-set analyses and accounts for population structure and relatedness. Follow the installed package’s documented input format and tutorial. This example deliberately does not imply that an arbitrary PGEN file can be passed directly to a STAARpipeline function.

Inputs
Unique IDs, sample counts, join cardinality, missingness, build, and allele orientation.
Computation
Synthetic fixtures, a small region, reference outputs, and failed edge cases.
Inference
Model diagnostics, multiplicity, LD/ancestry compatibility, and replication.

A small, inspectable R check

library(data.table)
ids <- c("s01", "s02", "s03")
pheno <- data.table(id = rev(ids), y = c(3, 2, 1))

stopifnot(!anyDuplicated(pheno$id))
stopifnot(setequal(pheno$id, ids))
aligned <- pheno[data.table(id = ids), on = "id"]
stopifnot(identical(aligned$id, ids))
stopifnot(identical(aligned$y, c(1, 2, 3)))

This synthetic fixture tests sample alignment. It does not validate an association model.

Dependencies: R and data.table. The three IDs and outcomes are synthetic. In a real workflow also check the genotype ID list, missing phenotypes, covariates, and the intended inclusion/exclusion rule.

Bounded research automation

  • One trigger: a scheduled check or a completed job.
  • One input: an approved status file or endpoint.
  • One output: a structured summary with provenance.
  • One stop rule: completion, failure, or a resource limit.

Notifications should identify an actionable change and link to its evidence.

Illustrative design for a monitor, not a claim that a local agent can safely access any cluster or messaging service. Verify destinations and allowed payloads before enabling notifications.

MCP connections

MCP standardizes how AI applications connect to tools and external systems.

Possible research uses

  • Search a permitted literature source
  • Read versioned reference metadata
  • Retrieve an approved job status

Connection review

  • Server owner and credentials
  • Read/write permissions and payloads
  • Source identifiers and retrieval date

A protocol connection does not establish source quality or data permission.

MCP introduction

Examples describe possible integrations. They do not assert that an official PubMed or gnomAD MCP server is installed or available in the audience’s environment.

A first task for the lab

  1. Choose a bounded changeFor example, a sample-alignment check in one script.
  2. Document the contractInputs, outputs, dependencies, and acceptance criteria.
  3. Use synthetic fixturesInclude a passing case and a case that must fail.
  4. Review and recordSave the diff and test results before broader execution.
A useful first task is small enough that a colleague can independently assess both the intended behavior and the test. Keep real-data access outside the task until the required permission and validation are in place.
